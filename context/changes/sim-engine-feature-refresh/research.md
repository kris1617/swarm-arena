## 1. Feature overview

The chosen flow: a signed-in user configures and runs a **client-staged** simulation (the "Start" button, not "Start on server") — from form submit through the composed per-tick pipeline to canvas rendering.

**Where input enters**: `src/app/simulation/page.tsx:932-937` — form submit calls `startRun.mutate(buildStartInput())` (`buildStartInput` at `page.tsx:363`, clamps 16+ fields including per-tribe `tribeConfigs`/`predatorTribeConfigs` against admin ranges). [evidence]

**Who validates it**: the tRPC `start` procedure (`src/server/api/routers/simulation.ts:601-609`) delegates to `insertRunningSimulation` (`simulation.ts:451-598`), which re-validates against admin ranges, applies a per-mutation rate limit, checks `MAX_PARALLEL_RUNS`, and — important correction from the prior analysis — **does not call `startServerRun` or anything in `server-run-registry.ts`**. The client-staged path (`start`) and the server-owned path (`startServer`) are structurally separate from the first database write onward; only the server-owned path uses the registry's `setInterval` tick scheduler. [evidence]

**Where state changes**: the client-staged path's entire tick loop runs in the browser. `simulation-canvas.tsx`'s seeding effect (`:811-851`) creates the initial population/predators via `~/server/simulation/boids` exports — the same functions the server-owned path uses — bundled directly into the client. Each `requestAnimationFrame` calls `computeSingleRunTick` → `runTick` (`single-run-lifecycle.ts:28,196` → `boids.ts:1681`), which composes the fixed pipeline `stepBoids → stepPredators → applyHunger → applyPredation → reproducePopulation` (`boids.ts:1770,1778,1810,1827,1911,1926`). A code comment at `boids.ts:1663-1673` asserts this inline sequence is kept in lockstep with the shared `runTick` function by hand — the same "two hand-synced call sites" risk the 2026-11-17 analysis flagged, confirmed still present and unchanged in shape. [evidence]

**What returns**: on each frame, `redraw()` (`simulation-canvas.tsx:686-735`) resolves the camera (`camera.ts:194`, `use-camera.ts:27`) and draws boids/predators colored from `entity.genes.color` (set at spawn, faded by energy), food colored from `FOOD_SEED_COLOR` (imported directly from `~/server/simulation/seed-colors`, bypassing `theme-colors.ts` entirely — a second instance of the client/server boundary question, not noted in the prior analysis), and canvas chrome colored from `theme-colors.ts`. On stop, `simulation.stop` persists the terminal state. [evidence]

**Per-tribe/predator-tribe config, threaded through this exact path**: `tribeConfigs`/`predatorTribeConfigs`/`flockCount`/`predatorFlockCount` flow from `buildStartInput` through `insertRunningSimulation` to `createInitialPopulation`/`createInitialPredators` on the client-staged path too. `TribeConfig` is now referenced in 9 files (`boids.ts`, `parameter-ranges.ts`, `single-run-lifecycle.ts`, `server-run-registry.ts`, `schema.ts`, `simulation.ts`, `simulation-canvas.tsx`, `server-run-viewer.tsx`, `page.tsx` — confirmed via `grep -l`, all 9 present), a config surface that didn't exist at the 2026-11-17 analysis (5 archived changes landed since: `per-tribe-behavior-weights`, `per-tribe-food-config`, `per-tribe-predator-config`, `predator-tribe-concept`, `second-predator-tribe-prey-target`). [evidence]

## 2. Technical debt

### 2.1 The cross-layer boundary break is real, open, and reversed direction since 2026-11-17

The prior analysis found `boids.ts` (server engine) importing color constants **from** `~/styles/theme-colors` (presentation layer) — a `server → styles` violation. **That exact violation is fixed**: `boids.ts:3-5` now imports `BOID_SEED_COLOR`/`PREDATOR_SEED_COLOR` from `~/server/simulation/seed-colors` (same layer), confirmed via `ast-grep run -p 'import { $$$ } from "~/styles/theme-colors"'` against `boids.ts` returning zero matches, cross-checked by `grep` (also zero). [evidence]

The direction reversed instead: `src/styles/theme-colors.ts:20-26` now re-exports `BOID_SEED_COLOR as BOID_FILL_COLOR`, `FOOD_SEED_COLOR as FOOD_FILL_COLOR`, `PREDATOR_SEED_COLOR as PREDATOR_FILL_COLOR` **from** `~/server/simulation/seed-colors` — confirmed via `ast-grep run -p 'export { $$$ } from "~/server/simulation/seed-colors"'`, exact match at those line numbers. This is the same edge today's `repo-map.md` flags as "confirmed still open" — both documents describe the current code correctly, but the 2026-11-17 research describes a now-fixed, opposite-direction problem. Both files' own comments document the re-export as deliberate (canvas rendering can't read CSS custom properties, so `seed-colors.ts` is kept as the single source of truth). Since there is exactly one definition and one honest re-export line, **no value can drift between the two files** — a "stays in sync" test would be structurally unnecessary; this is a documented, low-risk layering choice, not a live bug. [evidence]

**What's genuinely new**: `simulation-canvas.tsx:37` imports `FOOD_SEED_COLOR` directly from `~/server/simulation/seed-colors`, bypassing `theme-colors.ts` for one of the three colors it otherwise re-exports — plus `simulation-canvas.tsx` bundles a broad slice of `src/server/simulation/*` (boids, color, parameter-ranges, rng, single-run-lifecycle) directly into the client. This is a second, broader instance of the same client/server layering question the first boundary break raised, not examined by the 2026-11-17 analysis (which only looked at the server-owned path). [evidence]

### 2.2 Test coverage: mostly solid where the prior analysis worried, with new gaps in different places

**Per-tribe config family (per-tribe-behavior-weights, predator-tribe-concept, live crossbreeding) — well-tested, not an open gap.** The specific bug `lessons.md` records (matePreference seeded independently instead of per-tribe) is fixed and tested (`boids.ts:489-495,544-550`, asserted in `boids.test.ts:262,299`). Live-edit tests exist that prove actual downstream physics change, not just config round-tripping (`server-run-registry.test.ts:1636-1735` and a `preyTarget`-flip sibling). The "genes don't retroactively update on already-spawned individuals" boundary is deliberately tested as accepted behavior, not a silent gap (`server-run-registry.test.ts:1555-1587`). [evidence]

**One real, already-logged flake remains open**: `simulation.test.ts:3704-3724`'s `updatePredatorTribeConfigs` throttle-window test still uses two sequential real-wall-clock `await` calls — `lessons.md:117-122` already names this exact mutation under its "any `rejects a second call within the throttle window` test" recurring-flake entry, and its recommended fix (fake-timers/injected clock) has not been applied here. Medium priority — a known flake, not a correctness bug. [evidence]

**`camera.ts` (211 lines) has zero test file** — confirmed via `ls src/app/simulation/_components/camera.test.ts` (does not exist) against its sibling `depth-render.test.ts` (which tests analogous pure functions per `test-plan.md` §6.6's own cookbook pattern). Untested: `clampZoom`, `computeMinZoom`/`computeMaxZoom`, `updateAutoFollowCenter` (circular-mean centroid tracking across the toroidal wrap seam), `computeViewportRectOnMinimap` (a documented-as-accepted, unverified wrap-around edge case at `camera.ts:154-159`). The file's own header comment explicitly says it's "directly unit-testable without a canvas context," same posture as the functions `depth-render.test.ts` already covers. **Highest-priority gap found this pass** — cheap to close, matches an established pattern exactly. [evidence]

**`use-camera.ts` (151 lines, pan/zoom/wheel/ResizeObserver hook) has zero test file.** `test-plan.md`'s Risk #4 covers render-loop lifecycle but not camera input handling specifically; its own §6.2 cookbook pattern (happy-dom + stubbed RAF/pointer events) exists for exactly this shape of logic but was never applied here. Medium priority. [evidence]

**`server-run-registry.ts`'s untested retry-on-DB-failure pattern has tripled since 2026-11-17.** Confirmed via direct read (`server-run-registry.ts:781,791,809,816,819,840,848,852` plus the three field declarations at `186-194`): `wasEverThrottledWritten`, `wasEverFoodImbalancedWritten`, `wasEverPredatorTribeImbalancedWritten` are three copies of the identical "retry on next tick if the DB write fails" `.catch` branch. `grep -c` for all three names against `server-run-registry.test.ts` returns 0 — none of the three retry branches has a test forcing a DB failure to verify the retry actually happens. The prior analysis flagged this pattern for 1 field; it is now 3 untested copies of the same branch. Medium priority. [evidence]

**`startServerRun`'s double-registration throw (`server-run-registry.ts:899-901`) still has no direct test** (confirmed still open from 2026-11-17) — only its sibling `resumeServerRun`'s analogous guard is tested (`server-run-registry.test.ts:2485`). Low-medium priority, trivial to close (one-line assertion). [evidence]

### 2.3 Blast radius — wider than the structural-import graph shows, now measured

Today's `repo-map.md` flagged a known gap: `src/server/api/routers/simulation.ts` (sim-engine's own tRPC router) folds to `unmapped` in `capabilities.tsv`, so the structural import graph (Ca=6) understates sim-engine's true reach. This pass closes that gap by tracing every router-procedure caller directly (`grep -no "api\.simulation\.[a-zA-Z]*" <file>` across every app-layer file): the router is called from **8 route/component files** — `simulation/page.tsx`, `server-run-viewer.tsx`, `simulation-canvas.tsx`, `dashboard/page.tsx`, `leaderboard/page.tsx`, `runs/compare/page.tsx`, `runs/[runId]/page.tsx`, `admin/settings/_components/admin-settings-form.tsx` — effectively every major authenticated route in the product. [evidence]

**Schema/migration coupling**: `simulationRuns`'s `savedState` and `history` JSON columns must match `server-run-registry.ts`'s snapshot shape exactly (no schema enforcement beyond the comment naming the contract); `tribeConfigs`/`predatorTribeConfigs` JSON columns mirror the `TribeConfig` type defined in `boids.ts`; four sticky boolean markers (`wasEverThrottled`, `wasAutoStopped`, `wasEverFoodImbalanced`, `wasEverPredatorTribeImbalanced`) are derived facts, not raw inputs, explicitly not backfilled on old rows. Git co-change (138 commits touching `src/server/simulation/*` or the router): 15 (~11%) also touch `schema.ts`, 31 (~22%) also touch `simulation-canvas.tsx`, 3 (~2%) touch `theme-colors.ts`. [evidence]

**Tests that must actually re-run (not just exist) for a composed-tick contract change**: 16 files under `src/server/simulation/*.test.ts`, `simulation.test.ts` plus its 3 corpus-test siblings (whose exercise of the live tick path vs. pre-seeded rows remains **unconfirmed** — flagged unresolved in the prior pass, still unresolved here [unknown]), the 3 client-side mirror tests, `runs/export.test.ts`, and the shared `corpus-db-fixture.test.ts`. [evidence]
