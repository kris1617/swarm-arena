## Soft and client-only rules

- All four live-edit range checks (`checkLiveParamRangesSoft`, per-tribe, per-predator-tribe, per-run/concurrent object caps on `adjustLivePopulation`) are **soft** — bypass path: call the mutation directly (e.g. via a scripted tRPC client) with an out-of-range value; it applies and only a warning string comes back. This is stated as a deliberate design decision in the code comments (`simulation.ts:1441-1446`), not an oversight, but it does mean the admin-configured ranges are a *hard* ceiling at creation and only *advisory* for the life of a running simulation.
- The 500ms client-side Apply cooldown (`server-run-viewer.tsx`, not read this pass) is explicitly called out in comments as **client-only** and bypassable by a direct call — the real floor is the server-side `lastParamUpdateAt` check described above.

## Writers that work against a guard

- None found that actively reverse a guard. `applyLiveTribeConfigs`'s `foodStockShare` delta-injection (`server-run-registry.ts:391-410`) deliberately does NOT reset the live food pool on a config replace — called out by name in its own comment as intentional, not a bypass.

## Failure handling

- *Silently corrects*: `stop`'s `clampedElapsedTicks` (`simulation.ts:837-840`) — clamps an out-of-bounds `elapsedTicks` with no warning returned to the caller.
- *Silent default (not a failure, a designed fallback)*: the crossbreeding gate's `?.crossbreedingEnabled` undefined-reads-as-false (`boids.ts:1249-1250`).
- *Logged, not swallowed*: the three write-once DB markers (`wasEverThrottledWritten`, `wasEverFoodImbalancedWritten`, `wasEverPredatorTribeImbalancedWritten` in `server-run-registry.ts:781-866`) and `finishRun`'s own DB-write failure (`668-682`) all `console.error` on failure rather than swallowing silently, per the code's own comments. No named domain error type is used anywhere in this codebase — every failure is `TRPCError` with a generic code + a message string, or a `console.error`.

## Atomicity

- `getOrSeedAdminSettings` (`simulation.ts:179-247`) wraps its read + conditional backfill/seed write in one `db.transaction` — called out in a comment as "no other transaction use exists yet in this codebase."
- Every other multi-step business operation found (`insertRunningSimulation`'s rate-limit-check → parallel-cap-check → insert → two post-insert rechecks; `startServer`'s insert → concurrent-ceiling-check → `startServerRun` registration, each with a manual compensating `status:"stopped"` update on later failure) runs as **separate, non-transactional statements** with hand-written compensating writes rather than a DB transaction. This is a consistent pattern (not accidental — every failure branch explicitly flips the row to `"stopped"`), but it is not atomic: a crash between the insert and a compensating update would leave a `"running"` row with nothing tracking it (acknowledged directly in comments at `simulation.ts:636-642`, `646-666`, and `server-run-registry.ts:668-682`).
