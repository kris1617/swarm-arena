## One concept, many names

- Table `simulation_run` (schema.ts:98, snake_case via `createTable`) vs. TS identifier `simulationRuns` (camelCase) vs. domain concept "run" used throughout code comments and procedure names (`startServer`, `stopServerRun`, `LiveRun`) — same concept, casing differs by layer per ORM convention, not a drift.
- "Run" is both the DB row (`simulationRuns`, persists across the row's lifetime) and the in-memory ticking object (`LiveRun`, server-run-registry.ts:93, exists only while server-owned and active) — two different lifetimes under one English word. The code itself distinguishes them structurally (`isServerRunActive` checks the registry, not the DB status) but uses "run" for both in comments and function names (`stopServerRun` vs `insertRunningSimulation`).
- "Population" is used for (a) the generic `reproducePopulation<T>` helper's input array (either boids or predators, boids.ts:820) and (b) the general English sense of "population phase"/"population wipe" (single-run-lifecycle.ts:211) referring to the boid population specifically, not both species combined — same word, two different scopes (one generic-species, one boid-specific) in the same file set.
- `adjustLivePopulation` (server-run-registry.ts:298, the implementation) vs. `adjustLivePopulation` (simulation.ts:1075, the router procedure key) — identical name across layers but the router file aliases the import as `adjustLivePopulationRegistry` (simulation.ts:43) specifically to avoid the collision — the code's own comment flags this as deliberate, not accidental duplication.

## One name, many concepts

- `status`: three distinct state machines reuse this exact column name — `simulationRuns.status` (`"running"|"stopped"|"saved"`, schema.ts:130), `feedbackReports.status` (`"pending"|"sent"|"abandoned"`, schema.ts:205), and `ApplyLiveParamsResult`/the registry helpers' return shape (`{status:"applied"}|{status:"not-found"}|{status:"throttled"}`, server-run-registry.ts:202-205). Each is a separate domain lifecycle; only the field name is shared.
- `score`: `simulationRuns.score` (persisted final run score, a number) vs. `ParameterSuggestion.correlation`/no — actually distinct from "correlation" naming; but note `score` also appears as the raw per-row input to `pearsonCorrelation`'s `ys` array (parameter-suggestion.ts:123) — same field, reused as statistical input rather than a separate concept, not a true collision but worth flagging as dual-purpose.

## Implicit concepts

- **Hunger/starvation** has no dedicated type — lives only as `HUNGER_EXTRA_DECAY_RATE` (boids.ts:130) and a behavior inside `applyHunger` (boids.ts:956); the PRD requirement is cited in a comment (FR-008) but the concept itself is just "negative food stock causes extra lifespan decay," not a named state.
- **Predation/capture event** has no type — `applyPredation` (boids.ts:985) just filters a `Set<BoidState>` of captured boids out of the array each tick; there is no "CaptureEvent" or log of who captured whom.
- **Mating pair** is implicit — `reproducePopulation`'s `paired: Set<number>` (boids.ts:841) is a transient per-tick bookkeeping set, never a named/typed pairing entity.
- **Gender** is a two-valued field (`"a" | "b"`, boids.ts:47,70) with no further domain meaning attached in code beyond gating opposite-gender mating (boids.ts:899) — deliberately abstract, not "male/female."
- **Server-owned vs. client-staged run** is a structural distinction with no column of its own — determined entirely by presence/absence in the in-memory `registry` Map (`isServerRunActive`, server-run-registry.ts:402), an implicit concept load-bearing enough to gate `stop` vs `savePause` (simulation.ts:527-532).
- **Watcher** (someone currently viewing a live run) is tracked only as `watcherIds: Set<string>` (server-run-registry.ts:132) and `unwatchedSinceMs` — no `Watcher` type, just an id set keyed by subscription.

## States and transitions

- `simulationRuns.status`: `"running" → "stopped"` (via `stop` mutation simulation.ts:551, or `finishRun` server-run-registry.ts:443); `"running" → "saved"` (via `savePause` simulation.ts:1197); `"saved" → "running"` (via `resume` simulation.ts:1267). No transition back from `"stopped"`.
- `users.role`: `"member" → "admin"` (via `elevateSelf`/`elevateAccount`, user.ts:45-50, 83-89) and `"admin" → "member"` (via `revertSelf`/`revertAccount`, user.ts:56-58, 105-108), gated additionally by `elevatedUntil` timestamp semantics (comment schema.ts:50-55).
- `feedbackReports.status`: `"pending"` default (schema.ts:207) → presumably `"sent"`/`"abandoned"` via `attemptSendReport` (not opened — defined in `send-report.ts`, outside the read set; transition logic itself is an unknown here).
- `PopulationPhase`: `"establishment" → "growth" → "overshoot" → "crash" → "recovery" → "growth"...`, computed (not stored as a transition log, only as a time series) by `classifyPopulationPhase` (boids.ts:1329-1367) each tick from a windowed history.

## Where business logic lives

- Simulation stepping (boid/predator movement, steering, flee, capture, reproduction, scoring) lives entirely in domain-type-free pure functions in `boids.ts` — no class/domain-object layer; functions take plain state objects and params and return new state (e.g. `runTick` boids.ts:1058).
- Per-tick orchestration/decision logic (dt clamping, stop conditions, sample collection) lives in `single-run-lifecycle.ts`'s `computeSingleRunTick` — explicitly separated from the transport/UI shell per its own comment (single-run-lifecycle.ts:19-22).
- Server-run lifecycle (start/tick/snapshot/resume/finish, in-memory registry) lives in `server-run-registry.ts` — a module-level `Map` cached on `globalThis`, not a DB-backed state machine.
- Authorization/validation and DB writes live in the tRPC router (`simulation.ts`) — e.g. `checkAgainstAdminRanges`, `assertWithinConcurrentObjectCeiling`, ownership checks (`run.userId !== ctx.session.user.id`) are all router-level, not pushed into a service layer.
- No database constraints/triggers encode any business rule observed in this read — SQLite enum columns (`status`, `role`, `category`) are the only schema-level constraint; the "exactly one admin settings row" invariant is explicitly NOT a DB constraint (schema.ts:163-165 comment) and is enforced only by application convention (`ADMIN_SETTINGS_ID = 1`).
- This codebase has no dedicated `domain/`, `models/`, or `services/` directory (confirmed by 0-sources.md's own layer table) — types live beside the functions that use them, and "business logic" is split between `src/server/simulation/*.ts` (pure core) and `src/server/api/routers/*.ts` (validation/persistence/authorization), a two-layer, not three-layer, architecture.
