# Observability audit — simulation-start-stop, platform-plumbing (2026-11-13)

## 1. TL;DR

- **The one server-side error-capture boundary that exists is wired to fire only in development.** `src/app/api/trpc/[trpc]/route.ts:24-31`'s `onError` is `env.NODE_ENV === "development" ? ... : undefined` — confirmed at the `@trpc/server` library level that every throw site in `fetchRequestHandler` calls `onError?.(...)`, so with it `undefined` the call is simply skipped. Consequence: **any failure in `simulation.start`, `simulation.stop`, or `post.create` — a DB error, a race, a bug — leaves zero trace in `docker compose logs app`**, while the client still receives a perfectly correct error response. This is the single most consequential gap in the app.
- **The client-side RAF simulation loop (single-run and multi-run) has no exception boundary anywhere** — no `window.onerror`, no `unhandledrejection` handler, no React error boundary exist anywhere in `src/`. A future bug in the pure simulation math would freeze the canvas with absolutely no diagnostic trail, in the browser or on the server.
- **Two concrete TOCTOU races exist in `simulation.ts`** (read-check-then-write, no transaction, no affected-row check) that let a double-stop silently overwrite a score, or a double-start silently exceed the documented parallel-run cap — both resolve as ordinary-looking success responses.
- **Nothing in the entire app ever logs with a run id or user id attached** — even the one always-on log line (`[TRPC] ... took Nms`) and NextAuth's own default logger are identity-free, so fixing the `onError` gap alone would still leave a responder unable to correlate a log line to a specific run or user.
- **One concrete swallowed failure already exists in production-reachable library-default behavior**: `events.createUser` (`src/server/auth/config.ts:77-85`) assigns the admin role, but `@auth/core`'s `eventsErrorHandler` catches any exception from it, logs it only as a generic `EventError` via the library's own logger, and lets sign-in succeed anyway — a user can silently fail to get the admin role they should have, with no app-level signal that this happened.

## 2. Capture model

- **Runtime:** Next.js 16 App Router, Node standalone server (`output: "standalone"`, `next.config.js`), single long-running Docker container behind a Caddy reverse proxy (`context/deployment/deploy-plan.md`, `docker-compose.yml`). No background workers, queues, or cron — the only "background" execution is the client-side simulation tick loop (`requestAnimationFrame`) in the browser (`src/app/simulation/_components/simulation-canvas.tsx`, `src/app/simulation/multi/_components/multi-simulation-stage.tsx`).
- **Error tracker:** none anywhere in the codebase — verified against `package.json` and a full-tree grep (no Sentry/Datadog/Rollbar/Bugsnag/OpenTelemetry/New Relic).
- **Capture boundaries, by request path** (this is the key nuance both auditors converged on independently):
  - **Client-fetched tRPC calls** (`httpBatchStreamLink`, `src/trpc/react.tsx`) go through `fetchRequestHandler` (`src/app/api/trpc/[trpc]/route.ts:18-32`). Traced at the `@trpc/server` source level (`resolveResponse.ts`): every throw site calls `onError?.(...)` — optional chaining, so with `onError: undefined` in production the call is skipped entirely. **The client still gets a correct, well-formed error response** (status + shape, including Zod-flattened validation errors, `src/server/api/trpc.ts:47-56`); only server-side visibility is lost.
  - **Server-Component calls** (`src/trpc/server.ts`'s `createCaller`, e.g. `src/app/page.tsx:7`'s `api.post.hello`) never touch `onError` at all — they're in-process calls during RSC render. With no `error.tsx`/`global-error.tsx` anywhere under `src/app` (confirmed absent), Next's **built-in root boundary catches it and logs the full error to stdout by default** — this path *is* captured in `docker compose logs app`, just with no app-level correlation (only a `digest`, no identity).
  - `src/middleware.ts` (NextAuth's `auth` wrapper, `runtime = "nodejs"`) only gates by session presence; no app code wraps or logs anything here.
  - No client-side global error handler exists anywhere in `src/` (`window.onerror`, `unhandledrejection`, React error boundary) — confirmed by grep across the whole tree.
  - No `instrumentation.ts` exists anywhere in the app (confirmed by `find`; the only hits are inside `node_modules`/`.next` build artifacts) — Next 16's purpose-built `onRequestError` hook, designed to unify RSC + Route Handler + middleware error capture, is unused.
- **Logging:** exactly two `console.*` call sites in non-simulation app code, plus one in simulation code:
  - `src/app/api/trpc/[trpc]/route.ts:27-29` — dev-only, `.message` only (drops stack/cause), and gated off entirely in production regardless.
  - `src/server/api/trpc.ts:98` — unconditional timing line (`[TRPC] ${path} took ${end-start}ms`), fires on success and failure alike, carries no error or identity information.
  - NextAuth's own default logger (`node_modules/@auth/core/lib/utils/logger.js:7-21`, library code not app code) **does** print a full stack for every `AuthError`/`EventError` — the one place a real `Error` object (not just `.message`) reaches `console.error` in this app, but it's library-internal, not something app code controls or tags.
- **Scrubbing/sampling:** none — no tracker to configure.
- **Deploy identity:** `Dockerfile:14` sets `NODE_ENV=production`; no commit SHA, build id, or version string is read or logged anywhere in `src/`. `docker compose logs app` is append-only per container instance and resets on restart.
- **Production visibility baseline, confirmed with the project owner (not assumed):** the only way to see a production error today is SSHing into the VPS and running `docker compose logs app` — no tracker, no alerting, no log aggregation beyond Docker's raw stdout capture.

**Assumptions (outside the repo, not findings):**
- Docker daemon's log-driver/rotation settings (`docker-compose.yml` sets no `logging:` block) — host/daemon config, not in this repo. Unconfirmed.
- Whether `docker compose logs app` is checked proactively or only reactively after a user report — operational practice, not code. Unconfirmed.
- Caddy's own access/error logging (`Caddyfile`) — not reviewed this pass. Unconfirmed.
- Any VPS-level system log aggregation, alerting, or uptime monitoring entirely outside this repository. Unconfirmed.

## 4. Systemic root causes

1. **The one real server-side capture boundary (tRPC's `onError`) is wired to fire only in development** — `src/app/api/trpc/[trpc]/route.ts:24-31`. Confirmed at the `@trpc/server` source level that this is a simple skip (optional chaining), not a behavior change for the client. This single `env.NODE_ENV === "development"` ternary is the mechanism behind the biggest gap in the app: it explains PL-1 and, downstream, SS-4/SS-5/SS-6/SS-10 (every production failure in any client-fetched tRPC procedure, not just simulation's).
2. **No centralized, framework-level error-reporting hook is used** — `instrumentation.ts` (Next 16's `onRequestError`) doesn't exist anywhere in the app. Its absence is *why* capture is inconsistent by path: RSC calls happen to be logged by Next's unrelated default boundary, client-fetched tRPC calls are not, and nothing unifies or correlates either. Explains PL-3, and the asymmetry documented in §2/§3.
3. **No React error boundary exists at any level** (`error.tsx`/`global-error.tsx` absent repo-wide, confirmed by `find`) and **no client-side global handler exists either** (`window.onerror`/`unhandledrejection`, confirmed by grep). Together these mean every client-rendered exception — including a frozen RAF loop — is invisible beyond a generic page or a silently stuck canvas. Explains SS-2, SS-3, SS-14, PL-5.
4. **Every DB write in the audited flow trusts its own success with no affected-row or transactional check** — `simulation.ts`'s `start` checks only for an empty `.returning()` with no context (SS-6), and `stop`'s `.update()` result is never inspected at all (SS-7). This is what lets both TOCTOU races (SS-7, SS-11) resolve as ordinary-looking success responses instead of surfacing as anything unusual.
5. **Nothing in the app ever logs with a run id, user id, or correlation id** — not the one unconditional log line (`src/server/api/trpc.ts:98`), not NextAuth's own default logger, not the dev-only tRPC handler. Even a naive fix to root cause #1 (just flip the dev `onError` on) would produce a log line that can't be tied to a specific run or user without a manual DB query. Explains SS-10 and is a necessary companion to fixing #1.
6. **Mutation and event-callback failures are swallowed by default framework/library behavior, and the app never re-asserts the side effect it was relying on** — `events.createUser`'s admin-role assignment (PL-2) inherits `@auth/core`'s catch-log-and-continue `eventsErrorHandler` without the app checking afterward that the role was actually set; `post.create`'s mutation (PL-4) has no `onError` at all, so TanStack Query's internal failure handling produces no signal anywhere. Neither is a deliberate app decision — both are gaps left by never having had a reason to look.

## 6. Recommended fix order

Ordered by blindness removed per unit of effort:

1. **Wire `onError` in production** (closes PL-1, and by extension the server-side half of SS-4/SS-5/SS-6/SS-7/SS-10/SS-11). One file, `src/app/api/trpc/[trpc]/route.ts`. Log the full `error` object (not `.message`), `path`, and `ctx.session?.user?.id` — this single change gives every current and future tRPC procedure a server-side trace it has never had. No privacy concern beyond not logging request bodies with user-entered free text.
2. **Add a root `error.tsx`** (closes the display half of PL-5; cheap, ~10 lines, follows Next's own documented pattern). Pairs naturally with step 1 since both are "log the error, then decide what to show."
3. **Add `instrumentation.ts` with `onRequestError`** (closes PL-3). This doesn't replace step 1 (tRPC errors are skipped before reaching this hook when `onError` is `undefined` — actually once step 1 is done, both can coexist safely as two different layers), but it's the correct long-term home for anything beyond `console.error` and unifies RSC + Route Handler + middleware under one roof for the next audit.
4. **Fix the two TOCTOU races** (closes SS-7, SS-11) — requires touching `simulation.ts`'s write paths (affected-row checks or a `WHERE status = 'running'` guard on the update; a unique partial index or transaction for the start-cap check). More invasive than steps 1–3, but each is a real correctness bug wearing an observability costume.
5. **Add `onError` handlers to `post.create` and the single-run `stopRun.mutate`** (closes PL-4, SS-4, SS-3's logging half) — small, mechanical, same pattern repeated three times.
6. **Wrap the RAF `tick` callbacks in try/catch** (closes SS-2, and SS-14's risk) — the lowest-likelihood item (no known trigger today), but also the cheapest to add alongside step 5 while touching the same files.

No privacy constraint applies to any of the above — this app has no PII-scrubbing concern today since there's no tracker; logging the full error object everywhere above is safe as long as request payloads containing free-text user input aren't logged wholesale (none of the flows above take free-text input besides `post.create`'s `name` field, which is already low-sensitivity).

## 8. Method and limits

- **Agents run:** two parallel read-only subagents (one per `references/auditor-briefs.md` template) — an area auditor scoped to the simulation start/stop lifecycle (UI → tRPC → DB → score), and a plumbing auditor scoped to cross-cutting capture boundaries, middleware, logging, and a repo-wide sweep excluding the simulation area. Both were given the same capture-model draft up front and the production-visibility baseline confirmed with the project owner (no tracker; `docker compose logs app` only).
- **Spot-checked by hand** (per Step 5's "verify 3–5 most surprising/severe claims"): the tRPC `onError` dev-only gate (confirmed by direct read); `@auth/core`'s `eventsErrorHandler` swallow-and-log behavior (confirmed by reading `node_modules/@auth/core/lib/init.js:138-150`); the absence of any `instrumentation.ts` in app code (confirmed by `find`, distinguishing app-level absence from the unrelated hits inside `node_modules`/`.next` build artifacts); `post.create`'s missing `onError` (confirmed by reading `post.tsx`); the multi-run `stop` mutation's silent `onError` (confirmed by reading `multi-simulation-stage.tsx`). All five held exactly as reported; no findings were downgraded or dropped.
- **Deduplication:** both subagents independently identified the tRPC `onError` dev-only gate as the dominant gap (the area auditor from the simulation flow's perspective, the plumbing auditor via a direct `@trpc/server` library source trace establishing the full blast radius and confirming the client still receives a correct response). Merged into a single finding (PL-1) with the simulation-specific instances cross-referenced from the area table rather than double-counted.
- **Runtime proof:** not run this pass (`runtime_proof: not-run`). The audit found enough from static reading to produce an actionable, well-evidenced report; a before/after runtime probe (per `references/runtime-probes.md`, in an isolated worktree against a local fake-ingest endpoint) would be the natural way to prove fix #1 actually closes the gap once implemented — offered as a follow-up, not run speculatively.
- **Repo-wide sweep numbers** (plumbing auditor, excluding simulation territory, tests, `node_modules`): 2 `console.*` call sites total, 1 `.catch()` call (in the gated test-auth route, behaviorally correct), 0 empty `catch {}` blocks, 0 actual `try`/`catch` blocks in non-test app logic outside the test-auth route, 2 bare `throw new TRPCError` with no underlying cause to wrap (not findings).
- **Not verifiable from the repo:** Docker log-driver/rotation config, Caddy's own logging, any VPS-level aggregation/alerting/uptime monitoring, and whether `docker compose logs app` is actually checked proactively — all listed under §2's Assumptions, never used as findings or to raise/lower a severity.
