## Research Question

Ground rollout Phase 5 of `context/foundation/test-plan.md` (cross-cutting quality-gates wiring): the exact current CI/deploy setup, the correct GitHub Actions pattern to gate the existing deploy job on lint/typecheck/test passing first, and what secrets/env the new gate job genuinely needs versus what it must not have access to.

## Summary

- **`.github/workflows/deploy.yml` is the only workflow in the repo** (`.github/workflows/` contains exactly one file). It is a single `deploy` job, triggered on `push` to `master`, with one step that SSHes into the VPS using a GitHub Actions secret `DEPLOY_SSH_KEY` and runs no commands beyond the SSH connection itself (the actual deploy logic — `git pull --ff-only && docker compose build app && docker compose up -d` — lives in `/opt/swarm-arena/deploy.sh` on the VPS, triggered as a forced SSH command, confirmed via `context/deployment/deploy-plan.md`). The GitHub Actions job itself does no building, testing, or checking today — it is purely a remote trigger.
- **The correct pattern is a separate `test` job the `deploy` job depends on via `needs:`**, not inlining check steps into the existing job. This is both the standard GitHub Actions idiom for sequential gating and is required here specifically because the two jobs have a genuine least-privilege boundary: the `test` job needs Node/npm and zero secrets; the `deploy` job needs the `DEPLOY_SSH_KEY` secret and nothing else. A single combined job would give the test/lint/build steps unnecessary access to the deploy secret's execution context (not the secret's value directly, but the same job/runner scope) for no benefit.
- **No additional secrets or env vars are needed for the new gate job.** `vitest.config.ts`'s `test.env` block already sets `DATABASE_URL`, `NODE_ENV`, `AUTH_SECRET`, `AUTH_GITHUB_ID`, `AUTH_GITHUB_SECRET` as literal test values (confirmed in Phase 1-4 research this session) — `npm test` is self-contained and needs nothing from the CI environment beyond Node itself. `npm run typecheck` and `npm run check` (Biome) need no env vars at all.
- **`package-lock.json` exists and is committed** (confirmed via direct check) — `npm ci` is the correct install command for CI (deterministic, matches the lockfile exactly), not `npm install`.
- **One residual uncertainty, flagged honestly rather than assumed away**: `tsconfig.json`'s `include` array lists `.next/types/**/*.ts` and `.next/dev/types/**/*.ts` — directories generated by `next dev`/`next build`, and `.next/` is gitignored, so a genuinely fresh CI checkout (no prior `next dev`/`build` run) will not have these files. No `experimental.typedRoutes` flag is set in `next.config.js`, and no source file under `src/` imports from `.next/types` or `.next/dev` directly (confirmed via grep) — this strongly suggests the glob is inert create-t3-app boilerplate that matches zero files harmlessly rather than something `tsc` depends on. This project's own `.next/` directory already exists locally (from this session's earlier `npm run dev` runs), so this could not be verified empirically against a truly fresh checkout without disrupting the working dev environment — the new CI workflow's own first run against a fresh GitHub Actions runner is the actual, self-verifying test of this assumption.
- **No `engines` field in `package.json`** (confirmed) to pin a Node version for CI; local development uses Node v22 (confirmed via `node --version`) and `packageManager: "npm@9.2.0"` is declared.

## Detailed Findings

### Current deploy workflow (full content, `.github/workflows/deploy.yml`)

```yaml
name: Deploy to VPS

on:
  push:
    branches: [master]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Trigger deploy over SSH
        env:
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
        run: |
          mkdir -p ~/.ssh
          echo "$DEPLOY_SSH_KEY" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh -o StrictHostKeyChecking=accept-new -i ~/.ssh/deploy_key szef@217.154.238.241
```

- `context/deployment/deploy-plan.md` confirms the SSH key is "forced-command-restricted" on the VPS side — it can only run `/opt/swarm-arena/deploy.sh`, not an arbitrary shell. The actual `git pull`/`docker compose build`/`docker compose up` logic lives in that remote script, not in this workflow file. Adding a preceding gate job in GitHub Actions has no interaction with that remote script at all — it only controls whether the existing `deploy` job's SSH step runs.

### Commands to gate on

- `npm run typecheck` → `tsc --noEmit` (`package.json`)
- `npm run check` → `biome check .` (`package.json`)
- `npm test` → `vitest run` (`package.json`)
- All three confirmed runnable and passing against the current tree in this session (70/70 tests, clean typecheck, clean Biome check, repeatedly, across every rollout phase so far).

### Job-dependency pattern and secret scoping

- GitHub Actions' `needs:` key on a job makes it wait for the named job(s) to complete successfully before starting — the standard mechanism for "job B only runs if job A passed." Declaring `deploy: needs: test` is the idiomatic way to express this gate.
- The `test` job requires: `actions/checkout`, `actions/setup-node` (with `cache: npm`), `npm ci`, then the three check commands. None of these need `secrets.DEPLOY_SSH_KEY` or any other repo secret — confirmed by the env analysis above (vitest's env is self-contained; Biome and tsc need no env at all).
- The `deploy` job's existing `DEPLOY_SSH_KEY` secret usage is untouched; only its trigger condition changes (via `needs: test`), not its own steps or secret access.

### Install command and Node version

- `package-lock.json` exists and is tracked (confirmed `test -f package-lock.json` → true) — `npm ci` is correct (uses the lockfile exactly, fails if it's out of sync, faster than `npm install` for CI).
- No `engines` field in `package.json` to pin a Node version. Local dev Node is v22 (`node --version` → `v22.22.1`). `actions/setup-node`'s `node-version` input should be set explicitly (e.g. `22` or `lts/*`) since nothing else pins it.

### tsc dependency on `.next/types` — residual uncertainty

- `tsconfig.json`'s `include` (full list): `next-env.d.ts`, `**/*.ts`, `**/*.tsx`, `**/*.cjs`, `**/*.js`, `.next/types/**/*.ts`, `.next/dev/types/**/*.ts`.
- `.next/` is gitignored (`.gitignore:18`). `next.config.js` (full content read) sets only `output: "standalone"` — no `experimental.typedRoutes` or any other flag that would make application code depend on files under `.next/types`.
- A grep for `.next/types` and `.next/dev` across `src/` returned zero matches — no source file imports from these generated paths directly.
- This project's local `.next/` directory already exists (from earlier `npm run dev` runs in this session), so a true "fresh checkout, never built" scenario could not be tested empirically without removing dev state — this is stated as a gap, not papered over. The evidence (no typed-routes flag, no direct imports) points toward this being harmless, but the new CI workflow's first real run is the actual verification.
