## Verify a claimed commit-message fix is actually in that commit's diff

**Context**: commit aa5e0cf's message vs. src/server/simulation/boids.ts (basic-flocking-loop plan review, 2026-11-13)
**Problem**: A commit message claimed 5 bug fixes (unnormalized cohesion/alignment, no overlap floor, no cruise-speed floor, weak steering, duplicate distance computation) that weren't actually present in that commit's diff. The bugs were real and did eventually get fixed — just later, uncredited, as a side effect of an unrelated rewrite (S-02's predator-prey work), not by the commit that claimed them.
**Rule**: Before trusting a commit message's claimed fix (in a review, a changelog, or when deciding a bug is closed), verify the fix is actually present in that commit's diff — not just described in the message. A commit message is a claim, not evidence.
**Applies to**: /10x-impl-review and /10x-archive (when checking whether a plan's manual-verification claims hold); anyone writing a commit message — only describe a fix as done if its diff is in that same commit.

## HTML number inputs: `min` must not break the `step` grid for whole-number values

**Context**: `src/app/simulation/page.tsx` + `multi/page.tsx`'s "Energy threshold" field (genetic-inheritance-crossbreeding Phase 6, 2026-11-13)
**Problem**: The input was written as `min={0.0001}` with `step="1"` to express a zod `.positive()` constraint client-side. Browsers validate number inputs against `min + N*step`, so with `min=0.0001`/`step=1` the only valid values are `0.0001, 1.0001, 2.0001, ...` — every whole number (e.g. `22`) is silently rejected by native HTML validation, blocking form submission with no visible error until the user noticed the browser's "nearest valid values" tooltip. Caught only by a live manual browser check, not by any automated test (zod validation is correct server-side; the bug is purely in the client's HTML attributes).
**Rule**: For a "must be positive" numeric field, don't encode that as a fractional `min` — use `min={0}` (matching this file's own existing convention on `foodStockInitial`/other positive fields) and enforce strict positivity via a `Math.max(0.1, value)` clamp in the submit handler instead, exactly like the sibling fields already do. Never set `min` to a value that isn't aligned with `step` from the same base.
**Applies to**: Any new numeric form field in this project (or similar T3/React number-input forms) backed by a zod `.positive()`/`.min()` constraint — check `min`/`step` alignment, and prefer the established submit-time-clamp pattern over encoding the constraint in `min`.

## Procedurally-spread colors must anchor on the actual seed color's hue, not a fixed 0°

**Context**: `src/server/simulation/boids.ts`'s `createFlockColors` (genetic-inheritance-crossbreeding Phase 6, 2026-11-13)
**Problem**: Flock 0 reused the existing `BOID_FILL_COLOR` (hue ≈198°, a cyan-blue) as-is; flocks 1..N-1 were spread evenly starting from a fixed 0° (`(360/flockCount) * flockId`). For `flockCount=2`, flock 1 landed at exactly 180° — only ~18° away from flock 0's actual 198° hue — so the two "distinct" flocks were visually almost indistinguishable (both cyan-ish), defeating the whole point of per-flock color in the UI. All automated tests still passed, because they only asserted the two colors were *not byte-identical*, never that they were far enough apart to be visually distinct. Caught only by a live manual browser check.
**Rule**: When spreading N categories evenly around a color wheel (or any cyclic space) where one category reuses a pre-existing/fixed color, anchor the spread at that fixed color's actual position in the cycle — never at a hardcoded starting point (like 0°) — or small N can produce near-collisions depending on where the fixed color happens to sit. A same-byte-value-only test for "distinctness" is not sufficient for anything meant to be visually distinguishable; assert a minimum perceptual distance instead.
**Applies to**: Any future per-category color/identifier generation in this project; `/10x-plan`/`/10x-impl-review` reviewing similar "evenly distribute N things, one of which is fixed" logic — ask whether the fixed anchor's actual value was accounted for, and whether the distinctness test checks real separation or just inequality.

## tRPC subscription procedures cannot be invoked through `createCaller`

**Context**: `src/server/api/routers/simulation.ts`'s `watch` procedure (live-simulation-view-channel / roadmap F-04, 2026-11-14)
**Problem**: A plan draft assumed `watch` could be tested the same way `start`/`stop` are — via `createCaller().simulation.watch(...)`, matching `simulation.test.ts`'s existing pattern. tRPC v11's own types (`@trpc/server/dist/unstable-core-do-not-import-*.d.cts`) show `.subscription(...)`'s return type is `TCaller extends true ? TypeError<'Not implemented'> : SubscriptionProcedure<...>` — `createCaller`'s decorated procedures set `TCaller: true`, so invoking a subscription procedure through a server-side caller is a compile-time error, not a runtime one. Caught during `/10x-plan-review` by reading the shipped `.d.cts` files before any code was written, not discovered mid-implementation.
**Rule**: Never plan to test a tRPC subscription procedure via `createCaller`. Extract the subscription's generator logic into a plain, exported async generator function with no tRPC types in its signature (e.g. `watchServerRun` here) — tests call that function directly. The `.subscription(...)` procedure itself becomes a thin delegate (ownership/input validation already happened in the plain function if it needs DB access, or stays in the procedure if it's request-specific) that only adds `tracked()`'s SSE envelope; it is acceptable, and expected, for that thin delegate to have no independent test coverage.
**Applies to**: `/10x-plan` and `/10x-plan-review` for any future tRPC subscription procedure in this project — check the TCaller type signature before designing its test strategy around `createCaller`.

## SQLite's libsql client needs an explicit `busy_timeout` or concurrent test writers get spurious `SQLITE_BUSY` failures

**Context**: `src/server/db/index.ts` (run-export Phase 1, 2026-11-14, side-fix found while running the full suite)
**Problem**: `createClient({ url: env.DATABASE_URL })` never set a busy-timeout pragma. SQLite's default busy handler fails immediately with `SQLITE_BUSY`/"database is locked" instead of waiting, so once enough Vitest test files write to the same file-based `db.sqlite` under the default parallel-worker model, writers collide and tests fail intermittently — worse as more test files accumulate (this session hit it repeatedly across many phases, always "fixed" by retrying rather than root-caused, until adding a 20th concurrent-writer test file made the full suite fail consistently rather than occasionally).
**Rule**: Any new SQLite client in this project must set `PRAGMA busy_timeout = <ms>` once at creation (now done in `src/server/db/index.ts` itself, so this is already fixed project-wide) — never add a second db client elsewhere without the same pragma. If "database is locked" reappears, the fix is the timeout value or the write pattern, not another retry-until-green.
**Applies to**: Anyone touching `src/server/db/index.ts` or adding a new db connection; `/10x-implement` should recognize `SQLITE_BUSY` as a real, fixable bug rather than disposable flakiness if it recurs after this fix.

## tRPC router helpers must take `ctx.db` as a parameter, not the module-level `db` singleton

**Context**: `src/server/api/routers/simulation.ts`'s `insertRunningSimulation` helper (start-server-run-simulation / roadmap S-06, 2026-11-14)
**Problem**: A plan-review finding correctly flagged that threading `ctx` through an extracted helper was unnecessary complexity, and "fixed" it by having the helper read the module-level `db` singleton (from `~/server/db`) directly instead. That fix was wrong for this specific router: `simulation.test.ts`'s existing `describe("simulationRouter.start — parallel-run cap race")` test injects a sabotaging `Proxy` via `createCaller({ db: sabotagingDb, ... })` to reproduce an exact concurrent-insert timing — reading the global singleton instead of the `db` instance threaded through `ctx` would have silently bypassed that injection and broken the test. Caught only by actually running the full suite after the "fix," not by re-reading the code.
**Rule**: Any router-level helper extracted from (or shared between) tRPC procedures in this project must take `db` as an explicit parameter sourced from `ctx.db`, never the module-level singleton directly — even when the helper "obviously" doesn't need anything else from `ctx`. The singleton is fine inside non-router modules (e.g. `server-run-registry.ts`) that have no `createCaller`-based dependency-injection tests relying on a swappable `db`.
**Applies to**: `/10x-plan` and `/10x-plan-review` for any future router-level helper extraction in `src/server/api/routers/` — check whether an existing test overrides `db` via `createCaller({ db: ... })` before recommending a singleton-based "simplification."

## A 7-state-matrix plan dismissing "error" as N/A deserves a second look before implementation, not just at review

**Context**: `src/app/dashboard/page.tsx` (dashboard-restyle / roadmap S-16, 2026-11-14, a `/10x-ui`-driven audit)
**Problem**: The plan's Phase 3 explicitly reasoned the 7-state matrix's "error" cell was N/A for this view ("no form submission or error-producing action"), reasoning past the fact that the view's three `tRPC`/React-Query hooks (`listRunning`, `listSaved`, `listCompleted`) can themselves fail. With no `isError` check, a failed fetch would have rendered the page's "You haven't started any simulations yet." empty-state message — misleading during an actual outage, not merely cosmetic. Caught by `/10x-impl-review`'s Agent 2, not during planning.
**Rule**: Before marking the states matrix's "error" cell N/A for a view that reads from any query/fetch hook, check whether that hook's own `isError`/`isPending` flags are consulted anywhere in the render branch — a view with zero form submissions can still have a query-failure mode that "no error-producing action" glosses over. If the hook exposes an error flag the view ignores, "error: N/A" is the wrong call.
**Applies to**: `/10x-plan` and `/10x-plan-review` for any `/10x-ui`-driven change whose Phase marks a states-matrix cell N/A — verify the reasoning against the view's actual data-fetching hooks before accepting it, not just against its own JSX.

## "UI accepts input" is not "feature verified" — manual verification of a live-adjust feature must observe the actual effect

**Context**: `src/server/simulation/server-run-registry.ts`'s `LiveAdjustableParams` (live-parameter-adjustment / roadmap S-27, 2026-11-15; caught and fixed in `correct-live-parameter-field-set` / S-31)
**Problem**: S-27 shipped live-adjustment for `separationWeight`/`alignmentWeight`/`cohesionWeight`/`foodRegenRate`/`protectionThreshold`. Two separate rounds of manual verification (Phase 1's tRPC-level check and Phase 2's browser check) confirmed the mutation applied, the UI showed the new value, and a warning rendered for an out-of-range input — but never confirmed the simulation's actual *behavior* changed. It turned out `separationWeight`/`alignmentWeight`/`cohesionWeight` are per-boid genetic traits (`boid.genes.*`, set once at birth, inherited by blending parent genes) — the flocking calculation never reads the live-patched `run.params` value at all, for any boid, old or new. The feature's UI and persistence layer worked perfectly while doing nothing to the simulation for 3 of its 5 fields, and this survived both rounds of manual verification and a full impl-review undetected, because every check stopped at "the value changed in the data," never "the system's behavior changed as a result." The user caught it by direct domain knowledge of the codebase, not by anything in the verification process.
**Rule**: When a plan's manual verification step is for a "live-adjust X" / "toggle Y" / "change Z and see the effect" feature, the step must observe X/Y/Z's actual effect on system behavior (a different force vector, a different decision outcome, a different output on the next event it gates) — never stop at "the mutation succeeded and the stored/displayed value changed." Before writing such a manual-verification step, trace where the adjusted value is actually *read* at the point behavior is decided (not just where it's stored) and design the check around that read site. A value that's successfully written but never read at decision time is a defect the write-path alone can't surface.
**Applies to**: `/10x-plan` writing Manual Verification steps for any "live adjustment" or "toggle" feature; `/10x-impl-review` reviewing one — check that the manual-verification evidence traces to an actual behavior change, not just a persisted/displayed value change.

## A single green run of a test or test file proves nothing about flakiness — only repeated runs do

**Context**: `vitest-parallel-flakiness`'s Phase 5 stress-testing, 2026-11-16. This project's own `--no-file-parallelism` flag had been treated as the trusted "real" gate across several prior sessions/changes specifically *because* it reliably passed once per verification — nobody had run it repeatedly.
**Problem**: Running the same file group or the same full suite 5-40 times in a row (instead of once) surfaced two genuinely pre-existing, previously-undetected flaky tests (`simulation.test.ts`'s "lets an admin update ranges, and start enforces the new bound", and a cluster of `harness.test.ts` failures tracing to an already-accepted-but-wider-than-realized concurrent-widen risk) that fail 15-80% of the time depending on the specific test — including under the project's own "trusted" `--no-file-parallelism` gate, and even on commits that predate the change being verified. A single green run (or even 2-3) gave false confidence; the failure rate only became visible at 5+ repeated runs.
**Rule**: When verifying a fix for flakiness, or when establishing that a gate/test is "reliable," run it repeatedly (5-10+ times, not once) before trusting a green result — a single pass is not evidence of determinism, only evidence that it *can* pass. When a repeated-run batch surfaces an unrelated failure, isolate it (run that one file/test alone, repeatedly, and against the pre-change commit) before assuming it's caused by the change under test — a bug that predates the change and fails at a similar rate without the change is out of that change's scope and deserves its own follow-up, not scope creep into the current fix.
**Applies to**: `/10x-plan` writing Automated Verification criteria for any flakiness/race-condition fix — prefer "N consecutive runs" criteria over a single pass/fail; `/10x-implement` executing such a plan — don't declare a parallelism/race fix done after one green run; `/10x-impl-review` reviewing one — treat a Progress note that honestly documents "not literally N/N, here's why" as a positive scope-discipline signal, not a shortfall, over a note that silently claims full success.
